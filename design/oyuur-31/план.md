# OYUUR-31 «Лес в аккаунте 3: зашифрованная копия скрытых деревьев» — план

Основа: `design/oyuur-29/спец.md` (разделы 1–3, 5.2, 8.4, 8.6, 11.3–11.4, Т4, Т5), что уже сделано в OYUUR-30 (`design/oyuur-30/план.md`): записи и синхронизация, вход v2 без пароля (`net/kdf.ts` уже выдаёт `wrapKey`), сервер уже принимает и хранит `wrapP / wrapR / kid` и запись `vault` (непрозрачно).

## Коротко простыми словами
- Телефон придумывает **ключ данных** (32 случайных байта). Им запирается **сундук** — все деревья «Только я» с местами, наградами-желудями за них и удалёнными скрытыми привычками.
- Ключ данных лежит на сервере только в двух **шкатулках**: одну открывает пароль, другую — код восстановления. Ключ шкатулки получается из пароля (scrypt + HKDF, метка `oyuur/wrap/v1`) и с телефона не уходит; сервер получает только ключ входа (другая метка), из которого ключ шкатулки не получить.
- На телефоне ключ данных хранится в защищённом хранилище (`expo-secure-store`), в браузере — в хранилище сайта (там же, где и сам лес открытым).

## Алгоритмы (только стандартные, только проверенные реализации)
| Что | Чем |
|---|---|
| Пароль/код → ключи | scrypt (N = 2^15, r 8, p 1) + HKDF-SHA-256 — уже есть, `net/kdf.ts`, `@noble/hashes` |
| Запирание (шкатулки и сундук) | **AES-256-GCM**, `@noble/ciphers` (аудит Cure53), случайный nonce 12 байт на каждое запирание, метка 16 байт |
| Сжатие сундука | deflate, `fflate`; затем добивка нулями до кратного 4096 (размер не выдаёт число деревьев) |
| Случайные байты | `expo-crypto.getRandomBytes` (системный генератор) |

Отступление от Т4: в спецификации — XChaCha20-Poly1305; задача требует AES-256-GCM. Оба — стандарт, оба из одной проверенной библиотеки; nonce 12 байт случайный безопасен при нашем числе запираний одним ключом (≪ 2^32). Номер формата `v:1` закрепляет алгоритм.

### Форматы
```
kid   = base64url(sha256(DEK)[0..8])
wrapP = base64url(n(12) ‖ AES-256-GCM(wrapKeyP, n, aad = 'oyuur/wrap/p/v1/' + kid).encrypt(DEK))
wrapR = то же с wrapKeyR и 'oyuur/wrap/r/v1/' + kid
сундук: plain  = JSON {v:1, seq, trees (по id), places, ledger, tombs}
        packed = deflate(utf8(plain)); padded = u32be(len) ‖ packed ‖ нули до кратного 4096
        c      = AES-256-GCM(DEK, n(12), aad = 'oyuur/vault/v1/' + userId + '/' + seq + '/' + kid).encrypt(padded)
        body   = {v:1, kid, seq, n, c}   (base64url)
```
- В `aad` шкатулки — `kid` (а не `userId`: при создании аккаунта id ещё нет; ключ шкатулки и так свой у каждого аккаунта из-за соли). Распакованный ключ сверяется с `kid`.
- `seq` растёт с каждой версией сундука; телефон не принимает сундук с `seq` меньше уже виденного (откат), `seq` вшит в `aad`.
- Не открылся (испорчен, чужой ключ) → **сундук не трогаем и поверх не пишем**, лес на телефоне не стирается, состояние «Ошибка».

## Сервер (`server/`)
- `POST /api/auth/unlock` `{auth}` + сессия → `{wrapP, kid}` (v2; неверный → `401 wrong_password`; лимит 10/час).
- `POST /api/auth/keys` `{auth, recKdf, recAuth, wrapP, wrapR, kid}` + сессия — первые шкатулки для аккаунта v2 без ключа (перешёл в OYUUR-30): только если `key_id IS NULL` (кто первый); новый код (старый перестаёт работать). Уже есть → `409 has_keys` + `{wrapP, kid}`.
- `GET /api/sync` отдаёт ещё `kid` аккаунта; `GET /api/me` / `user` — `kid` и `vault: boolean`.
- Запись `vault`: `kid` конверта должен совпадать с `key_id` аккаунта (`409 wrong_kid`), без ключа у аккаунта — `409 no_keys`. Защита от сундука, который никто не откроет.
- Тест: в базе после синхронизации скрытых деревьев нет их названий ни в каком виде (поиск по файлу базы).

## Приложение
- `app/src/net/crypto.ts` (архитектор): ключ данных, шкатулки, сундук, ошибки `CryptoError` (`bad_key`, `wrong_kid`, `broken`, `rollback`); `app/src/net/dekStore.ts` (+ `.native.ts`) — хранение ключа данных.
- `state/friends.tsx`: ключ данных при создании аккаунта, входе (открыть шкатулку P), переезде v1→v2 и первом ключе (`/api/auth/keys`, новый код), восстановлении (шкатулка R → тот же ключ, новые шкатулки), смене пароля (новая P), новом коде (новая R), сбросе на телефоне (с ключом — тот же; без — `newDek`, сундук аккаунта пропадает), `lockHidden(password)` (кадры 14–17), выход/удаление стирают ключ.
- `state/records.ts`, `state/sync.tsx`: сундук = `chestOf()` (уже есть) — записывается зашифрованным, когда изменился (хеш открытого содержимого), сливается как остальные записи (`mergeRemote` по деревьям, местам, журналу желудей, надгробиям). Нет ключа / старый ключ → состояние `locked` («Скрытые деревья — только здесь · Запереть»), сундук не трогаем. Чужое «Стереть всё»: если сундук был в аккаунте — уходят и скрытые.
- Экраны: строка `locked` + лист «Запри скрытые» (14 → 15 «Запираем…» → 17 «Заперто» → новый код), «Позже» (больше сам не всплывает), восстановление с честной карточкой (06), «Новый пароль» на телефоне без ключа (09: тёплая карточка + красный диалог), подтверждение «показать друзьям» и подсказка «уберём с сервера сразу», новые тексты Политики и везде, где «скрытые не покидают телефон»; выход «убрать лес» доступен и со скрытыми, если сундук сохранён.
